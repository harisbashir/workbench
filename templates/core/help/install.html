Installing, backups & updates

Workbench runs as a single Docker container. Everything it stores goes in one data folder: the database, uploaded files, backups, and the encryption keys it generates on first start. There's nothing else to configure.

Install

On any machine with Docker (a Linux cloud server, a Windows or Mac PC, a NAS), in the Workbench folder:

docker compose up -d

Open http://<server>:8000. The first page asks for a setup code, which is printed in the log:

docker compose logs workbench

New server, straight from GitHub (recommended)

Your repository is private, so the server gets its own read-only deploy key. Copy install.sh to the server and run it with your repository's SSH address:

scp install.sh you@server:
ssh you@server
bash install.sh git@github.com:YOUR-ORG/workbench.git

It installs git and Docker, creates the key and shows it. Add it in GitHub under Repository → Settings → Deploy keys → Add deploy key (leave Allow write access off), press Enter, and the script checks GitHub's host fingerprint, downloads the newest release to /opt/workbench, asks for your domain (for HTTPS), starts Workbench and prints the setup code.

Already have a copy that was cloned over HTTPS? Run ./install.sh --deploy-key inside it to switch it to a deploy key.

HTTPS for internet access

If people connect over the internet, use HTTPS. Point a domain name (e.g. workbench.yourcompany.com) at the server, then:

echo "WORKBENCH_DOMAIN=workbench.yourcompany.com" > .env
docker compose --profile https up -d

A small Caddy web server is added that fetches and renews a free certificate automatically. Ports 80 and 443 must be open.

Without a domain, Workbench still works, for example inside a company VPN or over Tailscale. Administrators see a reminder banner about HTTPS.

Where uploaded files are stored

Administrators choose this in System → Storage. The options:

  • A folder on this server — the default, data/files. Can be pointed at a bigger disk or a NAS share mounted into the container.
  • Cloud storage with the S3 protocol: Amazon S3, Cloudflare R2, Backblaze B2, Wasabi, DigitalOcean Spaces, Google Cloud Storage (HMAC keys), or your own MinIO / Synology / QNAP S3 server. Choose the service and the address is filled in for you.
  1. Create a private bucket and an access key limited to it (on AWS, an IAM role on the server works without keys). It needs to list, read, write and delete objects.
  2. Enter the details and press Save and test connection. Workbench writes, reads back and deletes a test file.
  3. Press Move files and switch. Every file is copied and checked in the background; Workbench only switches when all of them made it, and people can keep working and uploading meanwhile. Nothing is deleted from the old place.
  4. With Lock storage here ticked (the default), the choice is permanent: the page only allows updating keys for the same bucket. To change it anyway, an administrator runs docker compose exec workbench manage storage --unlock on the server.
  5. The old storage stays available as a fallback until you press Stop using the old storage.

Keys are stored encrypted. Files are always downloaded through Workbench, so permissions apply wherever they're kept. With cloud storage, nightly backups still contain every file, and a copy of each backup is also kept in the bucket under backups/.

From the server: manage storage shows where files are, manage storage --test checks the connection.

Setting WORKBENCH_STORAGE in .env (as in version 1.2) still works and overrides the page.

Download everything

System & backups → Download everything creates a zip organised for people: every file in its folders, each firmware release with binaries and notes, BOMs and tasks as spreadsheets, and chat transcripts. Use it for handovers, audits or an archive. Restoring Workbench itself needs a backup instead.

Backups

  • A backup is taken every night automatically (the time is set in System → Backups). The newest 14 are kept.
  • Back up now takes one immediately, for example before an update.
  • Each backup is a single .zip containing the database, all files and the keys. Copy backups off the server regularly, e.g. by downloading them from the Backups page or syncing data/backups to cloud storage.

Restore

docker compose stop workbench
docker compose run --rm workbench restore workbench-20260925-020000.zip
docker compose start workbench

Your data from before the restore is kept in data/pre-restore-… until you delete it.

Update

cd /opt/workbench
./update.sh --check     # is there a new version?
./update.sh             # update

update.sh takes a backup, downloads the new version from GitHub, builds it while the current version keeps running, restarts and checks that Workbench is healthy. If the new version doesn't start, it goes back to the previous version and restores the backup by itself. ./update.sh --to v1.3.0 goes to a specific version. Everything is logged in data/update.log.

By default the server follows release tags (v1.3.0…), so pushing work-in-progress to main never reaches it. Install with --branch main to follow a branch instead.

Move to another server

Stop Workbench, copy the whole data folder to the new server, and run docker compose up -d there.

Monitoring

/healthz returns {"ok": true} when the database is reachable and there's enough disk space. Docker uses it for the container's health status, and you can point an uptime monitor at it.
