Firmware releases

Workbench records every firmware version you ship, with its binaries, release notes and the board revisions it runs on. It always knows which firmware belongs on which board and which version went into which production build.

Firmware and releases

  • A firmware is one image the product runs, for example Main application, Bootloader or Radio co-processor. Add them under the project's Firmware tab.
  • A release is one version of that firmware, such as 1.4.2. It has the files to flash, release notes, the git tag or commit it was built from, and the compatible board revisions.

Version numbers

Workbench uses semantic versioning, MAJOR.MINOR.PATCH:

ChangeExampleWhen
Patch1.4.2 → 1.4.3Bug fixes only
Minor1.4.3 → 1.5.0New features, still compatible
Major1.5.0 → 2.0.0Breaking changes, e.g. a new flash layout or protocol
Pre-release2.0.0-rc.1Candidates for testing before the final 2.0.0

Every release needs a new number, and a released version never changes. That's what makes firmware traceable.

From draft to production

  1. Draft: create the release, upload the image (.bin, .hex, .uf2…) and, ideally, the .elf with debug symbols. Write release notes and mention task IDs such as PWR-12.
  2. Testing: the team flashes it on test boards. Files can still be replaced.
  3. Released: the project lead (or an administrator) approves it. It needs at least one file and its compatible board revisions. The files are then locked, and older released versions for the same boards are marked deprecated automatically.
  4. Deprecated means a newer version replaced it. Recalled means it must not be used: give a reason, and everyone on the project is notified. Builds using it can't be started.

Controllers: which chip runs which firmware

A board can have more than one chip that runs firmware, for example a main MCU and a radio module. On the board's page, under Controllers, add each one with its designator (U1), a name and the part number, and tick the firmware it runs. A controller can run more than one firmware: a bootloader is flashed first, then the application.

Firmware for each board revision

On a revision's page, the Firmware panel lists every controller and its firmware. Choose the version each one ships with and press Save firmware. Workbench suggests the newest released version that's marked compatible with the revision, and warns you when:

  • a controller has no version chosen yet,
  • a version is recalled, deprecated or still in testing,
  • a version isn't marked compatible with the revision, or a newer one is available.

Once a revision is released for production, only released firmware can be chosen. A lead can lock the firmware so it can't change by accident; unlocking it is recorded in the audit log.

Production builds

A new build copies the firmware chosen on its revision. It's a snapshot: changing the revision later doesn't change what the build recorded. On the build page you can still change a version (released or testing), add another firmware, remove one, or copy the revision's firmware again. Each file's SHA-256 checksum is shown, and a build with recalled firmware can't be started.

Flashing bundle

The revision and build pages have a flashing bundle download: one zip with every image in flashing order, in folders like 01-U1-bootloader-1.0.0/, plus a manifest.json that lists each controller, firmware, version, file, SHA-256 checksum and flash order. Debug files such as .elf are left out. A bundle with recalled firmware can't be downloaded.

Checking a downloaded file

sha256sum firmware.bin                      # Linux / macOS
certutil -hashfile firmware.bin SHA256      # Windows

The result must match the checksum on the release page.

Automatic releases from GitHub

When you publish a GitHub release with a tag like v1.4.2, Workbench creates release 1.4.2 in Testing, with the GitHub release notes. Then attach the binaries. Each firmware has a tag prefix, so tags like boot-v1.0.0 can go to the bootloader instead. This needs the Releases event ticked on the GitHub webhook.
