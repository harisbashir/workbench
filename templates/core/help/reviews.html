Design & code reviews

Every schematic, PCB and firmware change goes through a pull request on GitHub, and every pull request is linked to a task. That gives one review process for code and hardware.

The flow

  1. Start the task. Drag it to In progress. Copy the suggested branch name from the task page (for example pwr-12-route-usb-c).
  2. Do the work in KiCad or your editor and commit to that branch. Mention the task ID in commit messages if you like — commits then appear in the task history.
  3. Open a pull request on GitHub. Workbench moves the task to In review and notifies the reviewer.
  4. CI runs (see below). If ERC/DRC or the firmware build fails, you're notified and the project channel gets a message.
  5. The reviewer reviews on GitHub. “Request changes” moves the task back to In progress; “Approve” is shown on the task.
  6. Merge. The task moves to Done.

Reviewing KiCad changes

KiCad files are text, but diffs of them are hard to read. The recommended GitHub Actions setup uses KiBot to produce, on every pull request:

  • Schematic PDF and PCB renders — review these instead of raw file diffs.
  • ERC and DRC reports — the pull request fails if either has errors.
  • A BOM CSV — download it and import it into the revision to see cost and stock impact.

An example workflow file is in the Workbench repository under docs/examples/kibot.yml.

Checklist for schematic and PCB reviews

  • ERC/DRC clean, or every waiver explained in the PR.
  • New parts exist in the parts library with a manufacturer part number.
  • No obsolete or “not recommended” parts (check the BOM page).
  • Compare the BOM with the previous revision (BOM page → Compare with…).
  • Decoupling, ESD protection, test points and footprints checked against datasheets.

Put review decisions in the pull request or in task comments so they're kept with the work.
