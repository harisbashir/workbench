Installing, backups & updates

Workbench runs as a single Docker container. Everything it stores goes in one data folder: the database, uploaded files, backups, and the encryption keys it generates on first start. There's nothing else to configure.

Install

On any machine with Docker (a Linux cloud server, a Windows or Mac PC, a NAS), in the Workbench folder:

docker compose up -d

Open http://<server>:8000. The first page asks for a setup code, which is printed in the log:

docker compose logs workbench

On a fresh Ubuntu or Debian server, ./install.sh does it all: it installs Docker, asks for your domain, turns on HTTPS and prints the setup code.

HTTPS for internet access

If people connect over the internet, use HTTPS. Point a domain name (e.g. workbench.yourcompany.com) at the server, then:

echo "WORKBENCH_DOMAIN=workbench.yourcompany.com" > .env
docker compose --profile https up -d

A small Caddy web server is added that fetches and renews a free certificate automatically. Ports 80 and 443 must be open.

Without a domain, Workbench still works, for example inside a company VPN or over Tailscale. Administrators see a reminder banner about HTTPS.

Where uploaded files are stored

By default, files live in data/files on the server. There are two alternatives:

  • Another folder or disk, such as a larger drive, a NAS mount or an AWS EBS volume. Mount it into the container and set WORKBENCH_FILES_DIR: 
    # docker-compose.override.yml
services:
  workbench:
    environment:
      WORKBENCH_FILES_DIR: /files
    volumes:
      - /mnt/nas/workbench-files:/files
  • Amazon S3, or any S3-compatible service such as Wasabi, Backblaze B2, Cloudflare R2 or MinIO. Add to .env: 
    WORKBENCH_STORAGE=s3
WORKBENCH_S3_BUCKET=acme-workbench-files
WORKBENCH_S3_REGION=ca-central-1
# Leave the keys out on AWS EC2/ECS and use an IAM role instead:
WORKBENCH_S3_ACCESS_KEY_ID=...
WORKBENCH_S3_SECRET_ACCESS_KEY=...
# Only for non-AWS services:
# WORKBENCH_S3_ENDPOINT_URL=https://s3.eu-central-1.wasabisys.com
    Keep the bucket private (block all public access). Files are stored encrypted (SSE-S3) and only ever downloaded through Workbench, which checks permissions. Nightly backups are also copied to backups/ in the bucket.

Moving existing files. To copy the files you already have into S3, run this with S3 configured, then set WORKBENCH_STORAGE=s3 and restart:

docker compose exec workbench manage migrate_storage --to s3 --dry-run   # see what will be copied
docker compose exec workbench manage migrate_storage --to s3
docker compose up -d                                                     # after changing .env

The command copies files and never deletes them, so you can run it again safely. --to local copies the other way.

The IAM policy needs s3:GetObject, s3:PutObject, s3:DeleteObject and s3:ListBucket on the bucket.

Download everything

System & backups → Download everything creates a zip organised for people: every file in its folders, each firmware release with binaries and notes, BOMs and tasks as spreadsheets, and chat transcripts. Use it for handovers, audits or an archive. Restoring Workbench itself needs a backup instead.

Backups

  • A backup is taken every night automatically (the time is set in System → Backups). The newest 14 are kept.
  • Back up now takes one immediately, for example before an update.
  • Each backup is a single .zip containing the database, all files and the keys. Copy backups off the server regularly, e.g. by downloading them from the Backups page or syncing data/backups to cloud storage.

Restore

docker compose stop workbench
docker compose run --rm workbench restore workbench-20260925-020000.zip
docker compose start workbench

Your data from before the restore is kept in data/pre-restore-… until you delete it.

Update

git pull
docker compose up -d --build

Database changes are applied automatically when the container starts. Take a backup first.

Move to another server

Stop Workbench, copy the whole data folder to the new server, and run docker compose up -d there.

Monitoring

/healthz returns {"ok": true} when the database is reachable and there's enough disk space. Docker uses it for the container's health status, and you can point an uptime monitor at it.
